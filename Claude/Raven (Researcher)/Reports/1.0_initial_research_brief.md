# 1.0 — Initial Research Brief

Three research threads, all needed to de-risk the Option A (local-first)
decision now that it's locked in.

## 1. Legal — Algerian data protection law, applied to this specific system
- Under Law 18-07 (amended by Law 25-11, 2025), does a system like this —
  internal to one institution, self-hosted on-premise, handling minors'
  health/psychological data — require formal declaration or authorization
  from the ANPDP (National Authority for Personal Data Protection)? What
  does that process actually involve?
- What does the law require specifically for **minors'** data and
  consent — is a parental consent step (paper-based, referencing the
  digital system) sufficient, or are there more specific requirements?
- Is there any existing guidance, precedent, or requirement around data
  retention periods for health data of minors in an Algerian healthcare
  context?
- Does self-hosting on Algerian soil satisfy any explicit "data
  residency" requirement in the law, or is that inferred/best-practice
  rather than a hard legal requirement? Be clear about which it is.
- **Flag clearly:** anything here that really needs an actual Algerian
  lawyer to confirm, rather than being resolvable through research alone.

## 2. Technical — self-hosted Supabase on-premise, realistically
- What are realistic minimum hardware specs for self-hosted Supabase
  (Docker Compose: Postgres + GoTrue + Realtime + Storage + PostgREST)
  serving a small internal user base (a few dozen staff accounts, not
  public traffic)?
- What are the common pitfalls/known issues people hit running this setup
  self-hosted long-term (upgrades, Realtime stability, backup gotchas)?
- What's a solid, well-documented backup strategy for the Postgres data
  in this setup (frequency, method, offsite copy handling)?
- Baseline WireGuard setup for allowing one or two remote users
  (coordinator) secure access without exposing the server publicly — is
  there a simpler alternative worth considering for a small non-technical
  maintenance team?

## 3. Technical — multilanguage / RTL implementation
The app must support multiple languages including Arabic (RTL) — this is
confirmed, not open. Research:
- Best-practice i18n setup for Next.js + Tailwind + shadcn/ui specifically
  (recommended library, e.g. `next-intl` vs. alternatives, and why).
- Known RTL issues/limitations in Radix primitives, TanStack Table, and
  cmdk specifically — anything that would affect Kernel's component
  choices or require workarounds.
- Practical guidance on structuring Tailwind classes for RTL support
  (logical properties vs. directional overrides) so this doesn't need to
  be redone later.

This should produce **implementation guidance**, not a language-selection
recommendation — which languages to support is a product decision for
Atom/the project owner, not Raven's call.

## Deliverable
Three findings reports (can be separate files or one combined report with
clear sections) in `Raven/Reports/`, following the report format above.
Flag anything urgent or blocking directly rather than waiting for the
next scheduled check-in.
