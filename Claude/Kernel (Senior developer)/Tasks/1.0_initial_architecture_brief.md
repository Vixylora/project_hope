# 1.0 — Initial Architecture Brief

## Decision (final, not up for re-litigation without Atom sign-off)
**Option A.** Local-first, on-premise hosting. No cloud deployment for
patient data at this stage.

## Stack
- **Frontend:** Next.js (App Router) + TypeScript, Tailwind CSS,
  shadcn/ui (Radix primitives), TanStack Table + TanStack Query, cmdk,
  React Hook Form + Zod, Framer Motion, Lucide icons.
- **Backend/DB:** Self-hosted Supabase (PostgreSQL + GoTrue Auth +
  Realtime + Storage + PostgREST), run via Docker Compose on a single
  on-prem server.
- **Hosting:** Server lives on the institution's internal network. Staff
  access via internal address/local DNS — no public internet exposure.
  Remote access (e.g., for the coordinator) via WireGuard VPN only.
- **Security:** Row-Level Security in Postgres enforces role-based data
  access at the database level — never rely on frontend hiding alone.
  This is Sentry's primary domain once tasks are broken out.

## Data model (source of truth: the paper form Atom has on file)
One patient → many sessions. Each session has four sections:
Educational, Psychological/Emotional, Health, Volunteer/Intern notes.
Full field-by-field breakdown should be requested from Atom if not
already provided — don't guess field names.

## Roles
`intern` (limited access), `psychologist` (full clinical access),
`coordinator` (broad oversight), `admin` (system/account management —
scope still being finalized between clinical vs. technical admin; build
the role as a distinct, separate role from `coordinator` so it can be
narrowed later without a schema change).

## Screens (full detail in Atom's UI spec — request it if not attached)
Login, Home/Dashboard, Logs, Patients list, Patient profile (near-
fullscreen dialog/sheet), Psychologists/Interns list, Personal info,
Settings.

## Team capacity note
This is being built by Kernel + Prism + Nexus + Sentry — not a solo
beginner build. That means local-first is realistically achievable fast,
but "fast" should still mean **phased**, not "everything at once":

**Recommended phase 1 (get this working end-to-end first):**
Docker Compose stack up, Postgres schema + RLS for the 4 roles, auth
(login), patient list, patient profile with session form (create/read),
basic role gating. No Realtime, no audit-log streaming, no animations
yet — get data flowing safely first.

**Phase 2:** Logs/audit trail (Postgres triggers + Realtime), Home
dashboard stats, search (cmdk), Framer Motion polish.

**Phase 3:** Psychologists/interns directory, personal info/settings,
VPN setup for remote access, backup automation.

Kernel should validate or push back on this phasing — it's a
recommendation, not a mandate.

## Constraints — non-negotiable
- **No real hospital name, patient names, or identifying details in the
  repo anywhere** — code, comments, seed/test data, commit messages, or
  Grok task files. This is a public repo. Use placeholder/fictional data
  for all examples and fixtures.
- All patient data access must be enforceable via RLS, not just UI logic.
- Health data is sensitive under Algerian law (Law 18-07/25-11) — no
  shortcuts on encryption, access logging, or minimization "for speed."

## Requirement — multilanguage (confirmed, not open anymore)
The app must support multiple languages, including Arabic with full RTL
layout, from the start — this is a confirmed requirement, not a decision
still pending. Practically:
- Frontend architecture should account for RTL from the beginning
  (Tailwind's RTL utilities, logical CSS properties over
  left/right-specific ones, RTL-aware component behavior in shadcn/Radix,
  TanStack, and cmdk).
- Set up an i18n solution early (e.g., `next-intl` or similar) rather
  than hardcoding strings — retrofitting translation into an already-built
  UI is significantly more expensive than building with it from day one.
- Exact language set and default language: confirm with Atom before
  locking content/copy, but the *architecture* should not block on that
  answer — build the switching mechanism now, fill in languages as
  confirmed.

Flag in your next report: any component in our chosen stack (Radix,
TanStack Table, cmdk) known to have poor or partial RTL support, since
that could affect component choices.
